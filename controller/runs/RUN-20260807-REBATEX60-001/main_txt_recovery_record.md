# 主方案TXT补齐与格式复核记录：RUN-20260807-REBATEX60-001

## 问题与复核结论

首版交付只有 `GJBTScheme/高级倍投主配置.txt`，5个号码方案仅保存为JSON定义，没有对应的软件主方案TXT。随后补TXT时虽然 `6-0` 等二星直选复式号码语法与历史字典一致，但生成器存在两个流程问题：

1. 将短横线拼接直接写死在生成器中，没有从机器可执行格式注册表读取；
2. 错把前二高级定码轮换的 `任选位置` 写成 `0,1`，而历史人工导入通过的013母版该字段为空。

本记录以历史验证档案重新冻结规则，并加入机器门控。

## 历史验证证据

已确认：

- `高级定码轮换 + 前二 + 直选复式` 曾由用户人工导入成功；
- `高级定码轮换内容`每局外层为 `局号|号码集合|参数1|参数2`；
- 直选复式各位置号段使用短横线 `-` 分隔；
- 每个号段为非空、不重复数字序列；
- 二星/前二必须正好2个号段；
- 已验证前二示例：`1|012-123|1|1`；
- 历史013前二直选复式母版：`任选位置=`为空、`换号期数=1`；
- 主方案使用GBK无BOM、CRLF；
- 高级倍投主配置使用UTF-8 BOM、CRLF。

因此，精确二码60不是写成一个整体 `60`，而是：第一位候选集合=`6`、第二位候选集合=`0`，按已验证的两段语法实例化为 `6-0`，完整局定义为 `1|6-0|1|1`。

## 防再次臆造的机器门控

新增：

- `controller/betting_format_registry.json`：投注数字格式机器唯一注册表；未知格式直接 `BLOCK_GENERATION`；
- `16_投注内容格式唯一源与防臆造门控协议.md`：规定“策略+玩法类型+玩法名称”必须先精确命中注册表；
- `tools/validate_betting_format_registry.py`：验证段数、分隔符、字符集、空值字段和正反例；
- `tools/build_front2_60_txt_bundle.py`：不再自行写死 `a-b`，改为调用注册表实例化具体号码；
- CI：必须运行格式注册表自检，并重新生成受门控的前二TXT样例。

机器门控明确拒绝本玩法的下列错误投注内容：`60`、`6 0`、`6,0`、`6|0`、`06-00`、`6--0`、`6-0-1`；同时拒绝 `任选位置=0,1`。
