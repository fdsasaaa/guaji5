# 主方案TXT补齐与投注语义复核记录：RUN-20260807-REBATEX60-001

## 问题演进

首版交付缺少5个可导入主方案TXT。补齐后又暴露两层问题：

1. 模板漂移：历史前二高级定码轮换母版的`任选位置=`为空，曾误写成`0,1`；
2. 更根本的投注语义错误：本批候选`28、49、60、81、02`的设计对象是**完整二位号码**，但此前为利用已有正式母版，错误选择了`前二 + 直选复式`，于是生成`2-8、4-9、6-0、8-1、0-2`这类位置集合格式。

`6-0`作为“前二直选复式两个位置候选集合”的语法可以成立，但它不是本任务要求的“完整二位号码60”的软件表达。数学结果集合可能相同，不代表软件玩法语义可以互换。

本次将该问题正式定性为：

```text
SEMANTIC_FORMAT_MISMATCH
```

## 字典证据

现有总字典明确：

- `前二 + 直选单式`投注内容示例为`08 50 89`；每一注是完整两位数字，多注使用ASCII空格分隔；
- `前二 + 直选复式`是两个位置的候选集合，号段使用`-`分隔；
- 投注格式必须同时由“承载策略 + 玩法类型 + 玩法名称”决定，不得跨玩法名称做所谓等价替换；
- `高级定码轮换 + 前二 + 直选单式`当前仍属于`low_confidence_derivation / test_only`，尚无足够人工导入证据升级成正式组合。

因此，本批5个投注对象应保持完整号码：

```text
28
49
60
81
02
```

而不是：

```text
2-8
4-9
6-0
8-1
0-2
```

## 语义 + 格式双门控

`controller/betting_format_registry.json`已升级：

- `EXACT_COMPLETE_TWO_DIGIT_NUMBER`：完整两位号码，强制`前二 + 直选单式`；
- `POSITION_SET_TWO_DIGIT_DIRECT_MULTI`：两个位置候选集合，才允许`前二 + 直选复式`；
- `semantic_mismatch_policy=BLOCK_GENERATION`；
- 完整号码`60`交给复式renderer时必须抛出`SemanticFormatMismatch`；
- `高级定码轮换 + 前二 + 直选单式`正式生成必须被门控阻断，只允许test_only验证包。

这意味着系统以后不能因为`60`与`6-0`在单一组合下可能覆盖同一结果，就擅自切换玩法名称。
